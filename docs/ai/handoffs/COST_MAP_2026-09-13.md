# Cost map — every Claude API call in SiteKick

**Read-only audit. No code changed, no model calls made.** Covers every place `lib/claude.ts`'s
`runStructured` is invoked, what each call actually sends, and where the real waste is. Ranked by
expected savings, not by file order.

## 0. Infrastructure gaps (affect every call below)

- **Zero token/cost tracking exists.** `runStructured` (`lib/claude.ts`) discards
  `response.usage` entirely — returns only the parsed tool result. There is no per-run, per-model,
  per-document, or per-action-type record of tokens or cost anywhere in the codebase today.
- **Zero prompt caching.** No `cache_control` block exists anywhere in the repo. Several agents
  (below) resend byte-identical large context across multiple calls in the same invocation — the
  single highest-leverage, lowest-risk win available, and it changes no business logic at all.
- **No prompt/model-version stamp on `documents`.** Dedup today is purely content-based
  (`external_id`, `content_hash`) — there is no `prompt_version` column, so there is no way to
  later say "reprocess only documents extracted under the old prompt." Not unsafe today (nothing
  reprocesses automatically), but it means a future prompt change has no clean, targeted replay
  path — it's all-or-nothing.
- **No input-size caps, no long-document approval gate.** `runStructured`'s only limit is
  `max_tokens` (output, defaults to 16000) — nothing caps *input* size or asks for confirmation
  before sending an unusually large document.

## 1. `agents/extract-comms.ts` — the biggest single target

**Every communication (email/transcript), one call each, Sonnet.** The prompt includes:
- The full project list (small, ~5-6 rows — fine).
- **The full list of every open task across the entire portfolio** — currently ~130+ tasks,
  unfiltered by project, sent to `taskList` (line 205-207) on **every single document**, regardless
  of whether that document is obviously about one property. This is exactly the pattern flagged:
  sending the whole task list + no narrowing before the model call.
- Rejected-patterns / verified-notes / match-decision blocks (small, capped, kill-switched — not a
  real cost driver).
- The document's own raw text (inherent, can't shrink without losing the extraction itself).

**Why this is real waste, not just "could be smaller":** the dedup rule this task list exists for
(SYSTEM's "CRITICAL dedup rule") only matters *within the same project* — a task on a different
property can never be the duplicate match. Most single communications name their property
somewhere in the text (a city case number, an address fragment, a project name in a subject line)
— that's a **deterministic, regex/substring-checkable signal**, computable in plain JS before any
model call. Proposed: before calling `extractComms`, scan `raw_text` for a literal match against
known project names / city_case numbers; if exactly one project matches, filter `taskList` to that
project's tasks plus null-project tasks (the existing dedup safety net already relies on this same
null-project category). Fall back to the full list only when no deterministic match is found (a
genuine multi-project weekly digest, still a minority of documents). **Expected effect:** for the
majority case (single-property correspondence), the task-list portion of the prompt drops from
~130 rows to typically under 20 — a meaningful fraction of this call's total input tokens, on the
single most frequently-invoked agent in the system (one call per uploaded/polled document).

**Model tier:** already Sonnet (`job: 'extract'`) — correct per the new rule (extraction/
attribution/ambiguity → Sonnet). No change needed here.

## 2. `agents/infer-phase.ts` — wrong model tier, no caching, on a rare-but-not-that-rare action

**"Infer from emails" (a project-page button click) → Opus, 2 or 3 full passes, every time:**
- Pass 1 (always) and Pass 2 (always, adversarial re-check) run on **Opus**, the most expensive
  tier, even though only Pass 3 (rare — only fires on disagreement between passes 1 and 2) is the
  kind of "explicit, rare, high-stakes judgment call" the new rule reserves Opus for.
- Pass 2's message **repeats the entire Pass 1 data payload verbatim** (up to 25 documents × 1500
  chars each = up to ~37,500 characters, plus the full open-task list for that project) just to
  append Pass 1's own answer at the end. Pass 3 (when it fires) repeats it a third time. This is
  the clearest prompt-caching case in the whole codebase — the shared prefix is byte-identical
  across calls within one invocation.

**Proposed:** downgrade Pass 1 and Pass 2 to Sonnet; keep Opus reserved for Pass 3 only (the actual
rare, adjudication step — matches "Opus only for explicit, rare action" exactly). Add a cache
breakpoint on the shared `dataMessage` prefix so Pass 2/3 don't re-bill the full document+task
payload. **Expected effect:** this is the single biggest per-invocation cost cut available —
2 of 3 calls move off Opus entirely, and the repeated large payload across passes stops being
charged at full price after the first call.

## 3. `agents/prioritize-tasks.ts` — already reasonably lean, one real gap

Sends every open task across the whole portfolio (~130+) **in one call**, not per-document — this
is the correct shape for a genuinely cross-project ranking task, not the same waste as extract-comms
(one call covers everything, not one call per item). Descriptions already truncated to 160 chars.
Job = `'digest'` → Sonnet, a reasonable fit ("ambiguity/judgment" per the new rule).

**The one real gap:** no idempotency check at all. "Refresh priorities" (manual button) and the
daily digest cron both call this with no check for "has anything relevant to the ranking actually
changed since the last run" — every click re-ranks the entire portfolio from scratch, even if
nothing changed. Confirmed live tonight: this ran 3+ times in one session for verification purposes
alone. **Proposed:** hash the fields that actually feed scoring (due/priority/status/waiting_for/
manual_priority/process_impact per task, blocker days_stuck/kind) and skip the call — reusing the
last run's output — when that hash matches the last run's. Low complexity, meaningful savings on a
Sonnet call sized to the whole portfolio.

## 4. `agents/daily-digest.ts` — already well-designed, no material waste found

Sends only pre-computed, already-summarized data (`topActions` capped at 8, `followUpAlerts`,
at-risk stages, Rowan invoice total) — never the raw task list or raw documents. Job = `'digest'`
→ Sonnet. This is the pattern the other agents should look more like. **No change proposed.**

## 5. `agents/triage-issues.ts` — already correctly tiered, already capped

Haiku (`job: 'triage'`), capped at 40 pending issue reports per run, sends only note bodies (no
task list, no history). This is exactly right per the new rule (Haiku for filtering/classification).
**No change proposed.**

## 6. `agents/parse-invoice.ts` — appropriately scoped

Sonnet (`job: 'extract'`), sends the PDF itself (inherent — the model has to read it to classify
it) plus small project/vendor name lists. No task list, no history. **No change proposed.**

## 7. `lib/auto-triage.ts` — not a cost item at all

Confirmed by direct read: **zero calls to `runStructured` or the Anthropic SDK anywhere in this
file.** The auto-triage learned-threshold system (safe-enrichment auto-apply, learned-reject
classes) is 100% deterministic rule/statistics code. Already free.

## What this does NOT touch (per explicit instruction — savings never justify guessing)

No proposed change here weakens date-provenance tagging, the human-feedback loop
(`priority_feedback`, verified notes, match decisions), or the Review Inbox's human-approval gate.
The task-list narrowing in extract-comms explicitly *keeps* the null-project fallback bucket so an
item with no property evidence still reaches review, never silently dropped. Nothing here changes
what gets auto-created vs. queued for a human — only what's *sent to the model* to reach the
same decision.

## Backlog/cron safety (already true, confirmed, not a gap)

The once-daily cron limits (`vercel.json`, Vercel Hobby plan) already prevent unbounded automatic
reprocessing — `process-import-queue` is capped at 15 documents/batch, `"Process all now"` has its
own time budget and a 2-consecutive-no-progress circuit breaker (both shipped last session). No
cron or backlog job runs without an explicit invocation and an existing bound; this matches the
"no auto-processing without budget/Preview" rule already, nothing new needed here.

## Recommended order, if authorized

1. **Prompt caching on `infer-phase.ts`'s repeated payload** — highest ratio of savings to risk,
   touches no business logic, purely an SDK parameter.
2. **Opus → Sonnet for infer-phase passes 1-2** — same file, same sitting, clear rule match.
3. **Deterministic project-narrowing of the task list in `extract-comms.ts`** — biggest absolute
   volume (every document), needs a bit more care (the fallback-to-full-list path must stay
   correct for genuine multi-project documents).
4. **Token/cost logging in `runStructured`** — needed to actually measure 1-3's real-world effect,
   and to answer "what does this cost" going forward. Infrastructure, not a savings source itself.
5. **Prioritize-tasks idempotency hash** — smaller win, low complexity, safe to do anytime.
6. **`prompt_version` column + input-size cap / long-document approval gate** — lower urgency,
   worth doing once 1-4 are settled, since they'll inform what "long" and "changed" should mean in
   practice.

Nothing above has been implemented. Waiting for direction on which of these (if any) to build,
and in what order.
