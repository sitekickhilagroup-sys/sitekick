## D-011 — Prioritization empty-run bug: read-side fix implemented
**Status:** Accepted, fulfilled. **Date:** 2026-09-07. **Authority:** Rotem (explicit: "אני רוצה
שתעשה את השינוי" — after Q-007's read-side half was independently verified by Claude against
`app/(dash)/(standard)/work/page.tsx` lines 108-118).
The read-side query in `app/(dash)/(standard)/work/page.tsx` (the "Latest AI prioritization run"
block, just above the AI-rank map) selected strictly the single newest `priority_runs` row by
`created_at`, with no check for linked `task_priorities` rows. Combined with the already-confirmed
write-side bug (`agents/prioritize-tasks.ts`'s `applyPrioritization` commits the `priority_runs`
row before the `task_priorities` rows), an empty run would silently replace a good prior one in
the UI — showing no AI ranks at all even though a real run exists.
**Fix implemented:** the query now fetches the 10 most recent `priority_runs` rows, fetches all
`task_priorities` rows for that set in one query, groups them by `run_id`, and picks the newest
run that has at least one linked row. `aiByTask`/`aiRunAt` (used throughout the rest of the page)
keep the same names and shapes, so no other part of the file needed to change — verified by
grepping every use of `aiByTask`/`aiRunAt`/`prioRows` in the file after the edit.
**Scope of this fix:** read-side only. The write-side ordering in `applyPrioritization` (insert
`priority_runs` before `task_priorities`) is unchanged — an empty run can still be created, this
fix only stops it from being surfaced ahead of a good one. A write-side fix (e.g. reversing insert
order, or wrapping both inserts in a transaction/RPC) is still open — see `OPEN_QUESTIONS.md` Q-007.
**Not verified by a test/build/lint run at the time this was written** — `device_bash` was
unavailable for the whole 2026-09-06/07 session, so this change could not be compiled,
type-checked, or exercised against real data before being written.
**Update (Claude, 2026-09-08):** the on-device sandbox became reachable and `npm run typecheck`
(`tsc --noEmit`) plus `npx eslint` were run against the changed file. Result: `tsc` reported 4
pre-existing, unrelated `Cannot find name 'PageProps'` errors (a Next.js ambient type normally
generated by `next dev`/`next build`, neither run in this environment; the same error appears in
three other route files this change never touched) — **zero errors on the new code itself**.
`eslint` on the file: clean. Full detail in `OPEN_QUESTIONS.md` Q-007. **Still not run:** an actual
`next build`/`next dev`, and the query against real/seed data — this is typecheck+lint evidence,
not a full green build or a confirmed-correct-behavior test.
**Consequence:** `docs/ai/CURRENT_STATE.md`'s "Known issue" moves from "not yet fixed" to
"read-side fixed and typecheck/lint-clean, write-side still open, not run against real data." Do
not describe this bug as fully closed until (a) a real build/dev run and a check against live/seed
data confirm behavior, and (b) the write-side ordering is separately addressed or deferred.
